# FSD 단계별 학습 가이드 (제로부터 숙련까지)

> **대상:** FSD를 **처음 듣는 사람**부터 **이미 익숙한 사람**까지 전원
> **목적:** 팀이 같은 그림을 갖고, **조금씩 이해도를 올려가며** 프로젝트를 진행할 수 있게 한다.
> **읽는 법:** 아래 **레벨**을 순서대로 읽되, 지금 필요한 곳에서 멈춰도 됩니다. 나중에 다시 와서 다음 레벨로.

| 레벨 | 누구를 위한 | 읽고 나면 |
|---|---|---|
| **Lv.0** 완전 처음 | FSD라는 말을 처음 들음 | "왜 폴더 구조에 규칙을 두는지" 감이 잡힘 |
| **Lv.1** 기초 | 용어는 들어봤지만 헷갈림 | 6개 레이어와 "의존 방향" 규칙을 말로 설명 가능 |

## Lv.0 — FSD가 도대체 뭐예요? (완전 처음)

### 한 문장으로
**FSD(Feature-Sliced Design)는 "코드를 어느 폴더에 둘지"를 정하는 약속**입니다.
"개발자 마음대로"가 아니라, **모두가 같은 규칙으로** 폴더를 나눠서, 누가 봐도 "이건 여기 있겠네" 하고 찾을 수 있게 하는 거예요.

### 왜 필요한가요? (규칙이 없으면)
폴더 규칙이 없으면 보통 이렇게 됩니다:
- 비슷한 코드가 여기저기 흩어져서 **중복**이 생긴다.
- 버튼 하나 고쳤는데 **엉뚱한 화면이 깨진다**(뭐가 뭘 쓰는지 모름).
- 새로 온 사람이 **어디서부터 봐야 할지** 모른다.
- 디자이너와 개발자가 **서로 다른 이름**으로 같은 걸 부른다.

FSD는 이걸 "**층(layer)을 나누고, 위층만 아래층을 쓰게**" 정리해서 막습니다.

### 비유로 한 번에
> **레고 상자**를 떠올려 보세요.
> - 맨 아래 칸엔 **기본 블록**(어디에나 쓰는 1×1, 2×4 블록) → 이게 `shared`.
> - 그 위 칸엔 **자주 쓰는 조합**(바퀴+축, 문짝) → `entities` / `features`.
> - 맨 위엔 **완성품**(자동차, 집) → `pages`.
>
> 규칙은 하나: **완성품은 블록을 꺼내 쓰지만, 기본 블록이 완성품을 알 필요는 없다.** (위 → 아래로만 참조)

이 "위에서 아래로만 쓴다"가 FSD의 **핵심 한 줄**입니다. 나머지는 다 디테일이에요.

## Lv.1 — 6개 레이어와 의존 방향 (기초)

FSD는 코드를 **6개의 층(레이어)**으로 나눕니다. 위에서 아래 순서:

```
app       ← 앱 전체 설정 (Provider, 라우터, 전역 스타일)
 ↓
pages     ← 라우트 = 화면 한 장 (로그인 페이지, 대시보드)
 ↓
widgets   ← 여러 조각을 합친 큰 UI 블록 (헤더, 사이드바)
 ↓
features  ← 사용자가 하는 "행동" (로그인하기, 장바구니 담기)
 ↓
entities  ← 비즈니스 "대상" (User, Product, Order)
 ↓
shared    ← 도메인과 무관한 범용 재료 (버튼, 색 토큰, 유틸 함수)
```

### 각 레이어를 한 줄로
| 레이어 | 무엇 | 예시 |
|---|---|---|
| **app** | 앱을 부팅하는 껍데기 | Provider, 라우터, 전역 CSS |
| **pages** | "화면 한 장" = 라우트 | `/login`, `/dashboard` |
| **widgets** | 여러 개를 묶은 합성 블록 | 헤더, 사이드바, 상품 카드 리스트 |
| **features** | 사용자 **행위** | "댓글 작성", "다크모드 토글" |
| **entities** | 비즈니스 **대상(명사)** | User, Product, Cart |
| **shared** | 범용 재료 (로직 없음) | Button, Input, 색/타이포 토큰, `cn()` |

> **헷갈림 방지:** `features`는 **동사**(행위), `entities`는 **명사**(대상). "장바구니에 담기"는 feature, "장바구니(Cart)" 자체는 entity. 자세한 구분은 [용어 사전](./fsd-glossary.md).

### 단 하나의 절대 규칙: **위 → 아래로만 import**
- ✅ `pages`가 `features`를 쓴다. `features`가 `shared`를 쓴다.
- ❌ `shared`가 `features`를 import (역방향 금지)
- ❌ 같은 레이어끼리 서로 import (예: feature A ↔ feature B) — 원칙상 금지

이 한 규칙 덕분에 **"아래층은 위층을 모른다"** → 버튼(`shared`)을 고쳐도 버튼은 누가 자길 쓰는지 모르니 **안전하게 재사용**되고, 의존 관계가 한 방향이라 **추적이 쉬워집니다.**

### shared 안은 또 4칸으로 나눔
`shared`는 가장 많이 쓰는 칸이라 안에서 또 나눕니다:
```
shared/
├── tokens/        ← 색, 타이포, 간격 (디자인 토큰)
├── components/ui/ ← 순수 UI 컴포넌트 (Button, Input …)
├── lib/           ← 유틸 함수 (cn(), 포맷터 …)
└── hooks/         ← 공용 훅 (필요할 때)
```

## Lv.2 — 우리 프로젝트(BO UI Kit)는 FSD에서 어디? (실전 진입)

여기가 우리 팀이 **꼭** 이해해야 하는 부분입니다.

### 결론: **이 저장소(bo-ui-kit) 전체가 곧 `shared` 레이어다.**
BO UI Kit은 **버튼·입력창·토큰 같은 "범용 재료"만** 모은 컴포넌트 라이브러리입니다. 비즈니스 로직(로그인, 주문 같은 것)이 전혀 없죠. FSD에서 그건 **정확히 `shared`의 정의**입니다.

> 팀 규칙 문서도 못박고 있어요: *"BO UI Kit 파일은 전부 `shared`"* ([figma-fsd-restructure-guide](./figma-fsd-restructure-guide.md) §9).

### 그럼 widgets/features/entities/pages는?
**여기서 미리 만들지 않습니다.** 그건 **이 킷을 가져다 쓰는 "실제 앱"의 몫**이에요.

```
┌─────────────────────────────┐        ┌──────────────────────────────────┐
│  bo-ui-kit (이 저장소)       │        │  실제 서비스 앱 (다른 프로젝트)   │
│  = shared 전부               │  npm   │                                  │
│  - components/ui (Button…)   │ ─────▶ │  app/                            │
│  - tokens                    │ import │  pages/   (대시보드 화면)         │
│  - lib                       │        │  widgets/ (헤더)                  │
│                              │        │  features/(로그인하기)            │
│  ※ 도메인 로직 없음          │        │  entities/(User, Order)           │
└─────────────────────────────┘        │  shared/  (← 여기서 bo-ui-kit 씀) │
                                        └──────────────────────────────────┘
```

- **킷(이 레포)**: "레고 기본 블록 상자"를 잘 만들어 둔다.
- **앱**: 그 블록을 꺼내(import) **필요에 따라** entities/features/widgets/pages를 조립한다.

### "필요에 따라 만든다"는 게 핵심
widgets/features/entities는 **미리 정의해 두는 게 아니라**, 앱에 실제 요구가 생길 때 **그때 슬라이스로 추가**합니다.
- 로그인 기능이 필요해졌다 → `features/auth-login` 추가
- "주문"이라는 도메인이 생겼다 → `entities/order` 추가
- 단, **아무 데나가 아니라** "이게 행위냐(feature)/대상이냐(entity)/합성블록이냐(widget)/화면이냐(page)"로 **레이어만 정해서** 넣습니다. (판단법은 Lv.3)

### 그래서 이 저장소는 지금 뭘 해야 하나?
**거의 아무것도 안 해도 됩니다.** 이미 개념상 통째로 `shared`라서요.
- (선택) 미래 대비로 **경로 별칭**(`@/shared/...`) 정도만 깔아두면 깔끔.
- 진짜 FSD 구조(pages/features…)는 **이 킷을 쓰는 앱이 생길 때 그 앱에서** 시작됩니다.
- 지금 억지로 `src/* → src/shared/*`로 옮기는 건 **비용만 들고(수십 곳 import·빌드 경로 변경) 이득이 0**입니다(통제할 상위 레이어가 여기 없으니까).

## Lv.3 — 직접 구조를 짤 때 (실전 / 숙련)

이 레벨은 **이 킷을 쓰는 앱**을 만들거나, FSD로 코드를 직접 배치하는 사람을 위한 것.

### 슬라이스(slice)와 세그먼트(segment)
- **슬라이스** = 한 레이어 안의 "기능 단위 폴더". 예: `features/comment-create`, `entities/user`.
  - `shared`와 `app`은 슬라이스가 없음(통짜). 슬라이스는 `entities`~`pages`에만.
- **세그먼트** = 슬라이스 *안*의 표준 칸:
  ```
  features/comment-create/
  ├── ui/        ← 컴포넌트 (보이는 것)
  ├── model/     ← 상태·로직 (store, 타입)
  ├── api/       ← 서버 통신
  ├── lib/       ← 그 슬라이스 전용 유틸
  └── index.ts   ← Public API (외부에 노출할 것만 export)
  ```

### Public API 규칙 (중요)
슬라이스 바깥에서는 **반드시 `index.ts`를 통해서만** import 합니다.
- ✅ `import { CommentForm } from "@/features/comment-create"`
- ❌ `import { CommentForm } from "@/features/comment-create/ui/CommentForm"` (내부 직접 접근 금지)

이유: 내부 구조를 바꿔도 `index.ts`만 유지하면 **바깥 코드가 안 깨짐**(캡슐화).
> `shared/components/ui`도 같은 원리: 배럴 `index.ts`로만 노출. (우리 레포의 `src/components/ui/index.ts`가 그 역할)

### "새 코드를 어디에 둘까?" 결정 트리
```
이 코드가 도메인/비즈니스와 무관한 범용 재료인가? (버튼, 포맷터, 토큰)
   └ 예 → shared
   └ 아니오 ↓
"명사(대상)"인가 "동사(행위)"인가?
   ├ 대상(User, Product …)          → entities
   ├ 행위(로그인, 좋아요 …)          → features
   ├ 여러 조각을 합친 큰 UI 블록      → widgets
   └ 라우트로 연결되는 화면 한 장     → pages
```

### 자주 하는 안티패턴 (피하세요)
| 안티패턴 | 왜 나쁜가 | 대신 |
|---|---|---|
| `shared`에 도메인 로직 넣기 | shared는 범용이어야 재사용됨 | 도메인은 entities/features로 |
| 역방향 import (`shared`→`features`) | 의존 방향 붕괴 → 추적 불가 | 위→아래 단방향 유지 |
| 같은 레이어끼리 직접 참조 (feature A→feature B) | 결합도↑ | 공통은 한 단계 아래로 내리거나 widget에서 합성 |
| 슬라이스 내부 파일 직접 import | 캡슐화 깨짐 | `index.ts`(Public API) 경유 |
| 모든 걸 미리 features/entities로 만들기 | 안 쓰는 빈 구조만 늘어남 | **필요할 때** 슬라이스 추가 |

### 디자인 ↔ 코드 매핑
디자인팀과 같은 언어를 쓰기 위해 Figma 구조도 같은 층으로 봅니다(자세히는 [디자이너 가이드](./fsd-designer-guide.md)):
- Figma의 BO UI Kit = 코드의 `shared`
- 앱 화면 Figma = 코드의 `pages`/`widgets`

## 자주 묻는 질문 (FAQ)

**Q. 우리는 지금 이 저장소를 FSD로 갈아엎어야 하나요?**
아니요. 이 저장소는 **이미 `shared` 그 자체**라 재구성할 게 사실상 없습니다. 별칭 정도만 선택적으로.

**Q. 그럼 FSD는 언제 본격적으로 쓰나요?**
이 킷(bo-ui-kit)을 **import해서 화면을 만드는 실제 앱 프로젝트**가 생길 때, 그 앱에서 pages/widgets/features/entities를 펼칩니다.

**Q. `entities`랑 `features` 진짜 헷갈려요.**
명사면 entity(주문 = Order), 동사면 feature(주문하기). "그 데이터 자체"인지 "그걸로 하는 행동"인지로 구분. → [용어 사전](./fsd-glossary.md)

**Q. shared 컴포넌트에 onClick 같은 로직 넣어도 되나요?**
UI 자체 동작(열림/닫힘 등)은 OK. 하지만 **비즈니스 로직**(주문 API 호출 등)은 안 됩니다 — 그건 feature의 몫.

**Q. 작은 프로젝트도 FSD를 꼭 써야 하나요?**
규모가 작으면 전체 레이어가 과할 수 있습니다. **shared만이라도 잘 분리**해두면 절반은 한 셈. 나머지는 커질 때 도입.
