# Figma → React 디자인 시스템 자동화 — 아키텍처와 설계 결정

> 이 문서는 "무엇을 만들었나"보다 **"왜 그렇게 만들었나"** 를 남긴다.
> 각 결정에는 대안·근거·치른 대가를 함께 적고, 실제 장애와 그로부터 바꾼 것을 기록한다.

---

## 0. 30초 요약

Figma 디자인 시스템(BO UI Kit)의 변경을 **사람 개입 없이 감지 → 추출 → 검증 → PR** 까지
자동화하고, 검증된 결과만 React 컴포넌트 라이브러리(npm `bo-ui-kit`)로 배포하는 파이프라인.

| 항목 | 수치 |
|---|---|
| 기간 | 2026-06-10 ~ 2026-08-06 (약 8주) |
| 컴포넌트 | 54개 (Figma 추적 노드 55개) |
| 코드 | `src` 기준 약 10,800 LOC (TS/TSX) |
| PR | 134건 (머지 119) — 이 중 **자동 생성된 sync PR 41건** |
| 헤드리스 실행 | 최근 34회 중 성공 28 / 실패 6 (실패 대부분 API 한도) |
| 배포 | `bo-ui-kit` (public npm), 120 files / 470KB |
| 실행 비용 | sync 1회당 **$2~6** (변경 규모에 비례) |

**핵심 주장**: 디자인→코드 동기화에서 어려운 건 *추출* 이 아니라 **"언제 반영할지"와 "믿을 수
있는지"를 정하는 일**이다. 이 프로젝트의 설계 대부분은 그 두 질문에 대한 답이다.

## 1. 문제 정의

디자이너가 Figma 에서 토큰 색을 하나 바꾸면, 개발자가 그걸 알아채고 → 값을 확인하고 →
코드를 고치고 → 리뷰받고 → 배포하기까지 **며칠이 걸리고 자주 누락됐다.** 특히:

- **누락**: 값이 아니라 *참조하는 토큰* 이 바뀌는 변경(재바인딩)은 육안으로 안 보인다
- **표류**: Figma 와 코드가 조금씩 벌어지면 "어느 쪽이 맞는지" 판단 비용이 계속 커진다
- **병목**: 확인 작업이 특정 개발자에게 몰린다

목표는 "자동으로 코드를 고치는 것"이 아니라 **"차이를 절대 놓치지 않고, 사람이 판단할
재료를 갖춘 상태로 올려놓는 것"** 으로 잡았다.

## 2. 시스템 개요

```
 디자이너: Figma 에서 Publish
        │
        ├─(즉시) Figma 웹훅 → Cloudflare Worker(중계) ─┐
        │                                              ├─→ GitHub repository_dispatch
        └─(15분 주기) 스케줄 폴링 ──────────────────────┘        │
                                                                ▼
                                            ┌────────────────────────────────┐
                                            │ figma-poll (2단 게이트)         │
                                            │  ① 새 발행 버전인가?            │
                                            │  ② 추적 노드가 실제로 바뀌었나? │
                                            └────────┬───────────────────────┘
                                     변경 없음 ◀─────┤ 실제 변경
                              (워터마크만 전진)      ▼
                                            ┌────────────────────────────────┐
                                            │ figma-sync (헤드리스 LLM 에이전트)│
                                            │  발행 스냅샷 기준 값 대조·추출   │
                                            │  → 브랜치 push → PR 생성        │
                                            └────────┬───────────────────────┘
                                                     ▼
                                            ┌────────────────────────────────┐
                                            │ visual (시각 회귀 + 증거)        │
                                            │  스냅샷 비교 / Figma·Before·    │
                                            │  After·Diff 이미지 코멘트        │
                                            └────────┬───────────────────────┘
                                        시각 변화 0 ─┴─ 시각 변화 있음
                                             ▼              ▼
                                        자동 머지      사람이 증거 보고 머지
                                                            │
                                                            ▼
                                                   npm publish (사람이 의도적으로)
```

**사람의 의사결정 지점이 3곳**이다: 디자이너의 **발행**, 리뷰어의 **머지**, 릴리즈 담당의
**publish**. 그 사이 기계적인 작업은 전부 자동이다.

## 3. 핵심 설계 결정

### 3.1 Figma 읽기 — MCP 가 아니라 REST API 로 통일

| | |
|---|---|
| **상황** | Figma 값을 읽는 경로가 둘: 공식 MCP 서버(대화형, 변수 *이름* 까지 제공)와 REST API(값만) |
| **대안** | (a) 수동은 MCP·CI 는 REST (b) 전부 REST |
| **결정** | **(b) 전부 REST** |
| **근거** | CI 는 헤드리스라 MCP 를 붙일 수 없다. 도구가 갈리면 "수동으로는 되는데 CI 에선 안 되는" 차이가 생기고, 그 차이를 디버깅하는 비용이 편의보다 크다. 실측으로 두 경로가 같은 값을 준다는 것도 확인했다(그림자·테두리 알파 등) |
| **대가** | 변수 **이름** 을 못 얻는다(Enterprise 전용 API). 그래서 토큰 매핑을 **이름이 아니라 값 기준**으로 한다 — 코드 토큰의 실제 색값과 노드의 fill 값을 대조 |

이 "값 기준 매핑" 제약이 나중에 중요한 규칙을 낳았다: **Figma 에 없는 토큰을 발명하지 말 것.**
과거에 테스트용 색을 보고 `--caution` 토큰을 만들었다가, 나중에 롤백할 때 바인딩 변경을
추적하지 못하는 원인이 됐다.

### 3.2 변경 감지 — 2단 게이트 (파일 버전 → 노드 지문)

| | |
|---|---|
| **상황** | Figma 는 autosave 마다 파일 `version` 이 올라간다. 이것만 보면 관계없는 편집에도 파이프라인이 돈다 |
| **결정** | ① 가벼운 `/versions` 로 버전 변화 감지 → ② **바뀐 경우에만** 추적 노드의 서브트리를 해시해 이전 지문과 비교 |
| **근거** | ①은 싸서 자주 돌려도 되고, ②는 비싸지만 드물게 돈다. 비용과 정확도를 분리 |
| **대가** | 지문이 **서브트리 전체 해시**라 레이어 이름변경·위치이동 같은 무의미한 구조 편집에도 "변경"으로 뜬다 → 이게 실제 교착을 낳았다([4.4](#44-구조-편집-no-op-교착)) |

### 3.3 릴리즈 신호 — "저장"이 아니라 "발행(publish)"

가장 늦게, 그러나 가장 크게 바꾼 결정이다.

| | |
|---|---|
| **문제** | 초기엔 *저장* 을 릴리즈 신호로 썼다. 디자이너가 작업 중 저장만 해도 코드에 반영되고, 소비처 입장에선 **예고 없는 시각 변경**이 나갔다 |
| **발견** | Figma `/versions` 응답에 `label` 필드가 있고, 라이브러리를 publish 하면 `"Components published"` 라벨이 **자동으로** 붙는다. 최근 15개 버전 중 8개가 라벨을 갖고 있었다 — 즉 디자이너의 명시적 릴리즈 의사표시가 이미 데이터에 있었는데 쓰지 않고 있었다 |
| **결정** | **이름 붙은 최신 버전**만 릴리즈로 취급. 무명 autosave 는 무시 |
| **효과** | ① 예고 없는 변경이 "디자이너가 의도한 릴리즈"로 바뀜 ② **autosave 노이즈 문제가 근본에서 소멸**(3.2 의 2단 게이트로 우회하던 것) ③ 추출을 발행 스냅샷(`?version=`)에 고정할 수 있게 되어, "발행 후 디자이너가 계속 편집해서 작업분이 섞이는" 레이스도 함께 사라짐 |
| **함정** | 전환 시 워터마크에 autosave id 가 기록돼 있어, id 만 비교하면 **더 오래된 발행본으로 역행 sync** 가 난다 → id 불일치 **AND 타임스탬프가 더 최신** 일 때만 변경으로 판정 |

### 3.4 추출 주체 — 헤드리스 LLM 에이전트 + 결정적 안전판

| | |
|---|---|
| **상황** | Figma 노드 JSON → React 컴포넌트 변환은 규칙화하기 어렵다(variant 조합, 조건부 스타일, 구조 판단) |
| **대안** | (a) 코드젠 규칙 엔진 (b) LLM 에이전트 (c) 사람 |
| **결정** | **(b), 단 앞뒤를 결정적 코드로 감싼다** |
| **근거** | 감지(무엇이 바뀌었나)는 해시로 결정적으로 할 수 있지만, 판단(이 변경을 코드에 어떻게 반영하나)은 문맥이 필요하다. 반대로 "PR 을 만들었나", "워터마크를 전진시켰나" 같은 절차는 LLM 에 맡기면 안 된다 |
| **구현** | 에이전트가 브랜치만 push 하고 PR 을 안 만들어도 워크플로의 안전판이 PR 을 생성한다. 워터마크·지문 기록도 워크플로가 보정한다([4.6](#46-에이전트-누락-보정)) |
| **대가** | 실행당 $2~6, 비결정성. 그래서 **모든 산출물이 시각 회귀와 증거 코멘트를 통과해야** 한다 |

### 3.5 검증 — 시각 회귀 + 증거 코멘트

플레이그라운드(전체 variant 갤러리)를 Playwright 로 스냅샷 비교하고, PR 에
**Figma 원본 / Before / After / Diff** 이미지를 코멘트로 남긴다.

핵심은 **증거 코멘트가 게이트보다 중요하다**는 점이다. 스냅샷 비교는 "달라졌다"만 말하지
"맞다/틀리다"를 말하지 못한다. 판단 재료는 Figma 원본과 나란히 놓인 렌더 이미지다.

### 3.6 머지 정책 — 전자동에서 2단계로 (되돌린 결정)

이 프로젝트에서 **유일하게 방향을 되돌린 결정**이라 기록해둔다.

- **처음**: 사람이 머지 → PR #150 이 **15일 방치**되고 파이프라인 전체가 멈춤([4.2](#42-15일-정지))
- **그래서**: 자동 머지 도입 (재검증 green 이면 머지)
- **그런데**: 그 "재검증 green" 이 **동어반복**이었다. 시각 변경을 감지하면 새 렌더로
  baseline 을 덮어쓴 뒤 다시 비교하므로 **자기 자신과의 비교**다. 렌더 플레이크만 잡을 뿐
  디자인 변경이 옳은지는 전혀 검증하지 못한다
- **최종 (2단계)**: 시각 diff **0** 이면 자동 머지 / 시각 변화가 있으면 라벨 붙이고 **사람이
  증거 보고 머지**

**교훈**: "자동 vs 수동" 은 잘못된 프레임이었다. 진짜 문제는 *검토 대기가 파이프라인 전체를
막는 구조* 였고, 그건 dedup 을 발행 버전 단위로 바꿔 해결했다. 그러고 나니 사람 검토를
되살려도 안전해졌다.

### 3.7 패키징 — 한 저장소, 두 출구

```
src/components/ui/  (단일 소스)
   ├─→ 플레이그라운드 (Vercel)  : 디자이너·개발자가 눈으로 확인
   └─→ npm dist (bo-ui-kit)     : 소비 프로젝트가 import
```

`files: ["dist"]` 로 **배포물에는 컴포넌트 알맹이만** 들어간다(스토리·플레이그라운드 제외).
저장소를 쪼개지 않은 이유: 소스가 한 벌이어야 "플레이그라운드에서 본 것"과 "설치한 것"이
같다는 보장이 쉽다. 배포 경계는 저장소가 아니라 `files` 필드로 긋는 게 더 싸다.

### 3.8 토큰 표현 — RGB 채널 CSS 변수

`--primary: 43 127 255` 처럼 **채널만** 저장하고 Tailwind 에서 `rgb(var(--primary) / <alpha-value>)`
로 노출한다. `bg-primary/90` 같은 불투명도 유틸을 그대로 쓰기 위해서다.
토큰 단일 소스(`src/tokens.css`)를 앱과 라이브러리 빌드가 공유해 이중화를 막았다.

## 4. 장애 사례

실제로 터진 것들. 각각이 위 설계 중 하나를 바꿨다.

### 4.1 웹훅이 조용히 죽음 (2주간 미감지)

| | |
|---|---|
| **증상** | Figma 저장이 있었는데 웹훅 경유 실행이 6/18~7/2 **0건**. 그런데 웹훅 상태는 `ACTIVE` |
| **조사** | Cloudflare 30일 지표: 요청 0, 에러 0 → Worker 는 멀쩡. Figma 발송 이력 API(`/v2/webhooks/:id/requests`) 조회 → **발송 기록 자체가 0건**. 즉 Figma 가 보내려는 시도조차 안 했다 |
| **원인** | Figma 내부에서 웹훅 레코드가 죽음(외부에서 확인 불가). 재등록이 유일한 처방 |
| **조치** | passcode 재발급 → 구 웹훅 삭제 → 재등록 → 가짜 이벤트로 엔드투엔드 검증 |
| **교훈** | **`status=ACTIVE` 는 신뢰할 수 없다. 발송 이력이 진실이다.** 그리고 이 2주간 파이프라인이 멈추지 않은 건 15분 폴링 백업 덕분이었다 — **푸시와 폴링의 이중화가 실제로 값을 했다** |

### 4.2 15일 정지

| | |
|---|---|
| **증상** | sync PR #150 이 15일간 머지되지 않았고, 그동안 **후속 디자인 변경이 하나도 반영되지 않음** |
| **원인** | 두 겹. ① 그때는 "재검증 → 머지"가 작업 세션에 의존했는데, PR 이 세션 종료 18분 뒤 생성돼 아무도 그 단계를 밟지 않음 ② 더 나쁜 건, PR 에 연결된 이슈가 안 닫히자 poll 의 **dedup 이 이후 모든 sync 를 차단** |
| **조치** | 자동 머지 도입 → (나중에) 2단계 정책 + **dedup 을 발행 버전 단위로 변경** |
| **교훈** | 원인 ②가 진짜 문제였다. ①만 고쳤다면 같은 사고가 형태만 바꿔 재발했을 것이다. **"막힘"의 원인과 "안 돌아감"의 원인을 분리해서 봐야 한다** |

### 4.3 좀비 PR 부활

| | |
|---|---|
| **증상** | 머지·삭제한 브랜치로 PR 이 되살아났고, 그대로 머지했다면 최신 main 을 **역행**시킬 내용이었다 |
| **원인** | 머지 후 **늦게 도착한** baseline push 가 삭제된 브랜치를 재생성 → 다음 sync 의 "PR 없으면 만든다" 안전판이 그 stale 브랜치로 PR 을 생성 |
| **조치** | 브랜치 팁 SHA 가 **닫힌/머지된 PR 의 head 와 같으면** 부활 금지 |
| **교훈** | 안전판(자동 복구 로직)도 상태를 잘못 읽으면 사고를 만든다. **"없으면 만든다" 류의 복구 로직엔 반드시 "왜 없는지"를 구분하는 조건이 필요하다** |

### 4.4 구조 편집 no-op 교착

| | |
|---|---|
| **증상** | poll 이 19개 컴포넌트 변경을 감지해 이슈+sync 를 돌렸는데, 에이전트는 "코드에 반영할 값 변경 없음"으로 PR 없이 종료. 워터마크·지문이 안 전진하고 이슈도 안 닫혀 **또 교착** |
| **원인** | poll 의 지문은 *서브트리 해시* 라 레이어 이름변경·이동에도 반응하지만, 에이전트는 *실제 디자인 값* 을 보므로 판정이 갈렸다 |
| **조치** | 에이전트가 성공 종료 && 열린 sync PR 없음 && 버전 게이트는 여전히 "변경" 이면 → 지문·워터마크를 전진시키고 이슈를 닫는 **자가 치유** 스텝 |
| **교훈** | 게이트가 여럿이면 **판정 기준이 다를 수 있고, 그 불일치가 교착이 된다.** 불일치를 해소하는 주체를 명시적으로 두어야 한다 |

### 4.5 시각 baseline 의 취약성

| | |
|---|---|
| **증상** | 사이드바 목록 **순서만** 바꿨는데 19개 스냅샷이 ~1% diff 로 실패. diff 위치는 텍스트가 있는 곳마다 흩뿌려짐 |
| **원인** | Pretendard 폰트를 CDN 에서 로드 → 첫 페인트 내용에 따라 적용 타이밍이 미세하게 달라지고, **텍스트 안티앨리어싱**이 baseline 과 어긋남. 임계값이 빡빡해서(색만 살짝 바뀌는 회귀를 잡으려고) 이걸 통과시키지 못함 |
| **조치** | **폰트 self-host** (같은 버전 정적 파일 → 글리프 동일, 로드는 결정적) |
| **교훈** | 시각 회귀 테스트의 적은 컴포넌트 버그가 아니라 **비결정성**이다. 네트워크에 의존하는 리소스는 테스트 환경에서 제거하는 게 임계값을 조절하는 것보다 낫다 |

### 4.6 에이전트 누락 보정

에이전트가 매니페스트 워터마크 전진을 빠뜨리면 → 지문이 구버전으로 기록 → poll 이 영구
재감지 → dedup 교착. 또 PR 본문의 `Closes #N` 이 처리되지 않는 경우도 있었다.

→ **둘 다 워크플로가 결정적으로 백업**하도록 이중화했다. 브랜치 매니페스트 값이 main 과
같으면 누락으로 보고 보정하고, 머지 후 이슈를 명시적으로도 닫는다.

**교훈**: LLM 에이전트에 절차를 맡길 때는 "지시했으니 됐다"가 아니라 **결과를 코드로
검사하고 보정**해야 한다.

## 5. 신뢰 경계와 보안

- **프롬프트 인젝션 표면**: 헤드리스 에이전트가 Bash + repo write 권한을 가진 채 **Figma 파일
  콘텐츠(텍스트 레이어 포함)를 읽는다.** 즉 Figma 편집 권한자는 디자인 안의 텍스트로 에이전트에
  지시를 주입할 수 있다. → **Figma 편집 권한 = 사실상 repo write 권한** 으로 간주해야 한다.
  현재 방어선은 시각 게이트 + 증거 코멘트 + (이제) 사람 머지다.
- **시크릿 분리**: Figma PAT·Claude 토큰은 GitHub Actions Secrets, 웹훅 중계자의 GitHub PAT 과
  passcode 는 Cloudflare Secrets. 저장소 코드엔 참조만 있다.
- **중계자 검증은 fail-closed**: passcode 시크릿이 미설정이면 전부 401(열리는 게 아니라 잠김).
- **알림 사고 방지**: PR/커밋 본문의 백틱 없는 `@조직명` 이 GitHub 멘션으로 해석돼 팀 전체에
  메일이 나간 적이 있다(실제 사고). 이후 로컬 훅 + CI 가드 + 자동 sanitize 3중으로 차단.

## 6. 측정 가능한 결과

| 지표 | 값 |
|---|---|
| 디자인 변경 → PR 생성 | **수 분** (발행 즉시 웹훅, 백업 폴링 15분) |
| 자동 생성된 sync PR | 41건 |
| 감지 누락 | 0건 (폴링 백업이 웹훅 2주 장애를 전부 커버) |
| 놓칠 뻔한 변경 | Meter 인디케이터의 **토큰 재바인딩** — 색 *값* 은 그대로였고 참조 토큰만 바뀌어 육안·값 비교로는 안 잡히는 유형 |
| 헤드리스 비용 | sync 1회당 $2~6 |

## 7. 알려진 한계와 다음 단계

| 한계 | 상태 |
|---|---|
| **다크 모드 미검증** | Figma 각 컴포넌트 페이지에 `Dark Mode Preview` 프레임이 실재하지만, 코드의 `.dark` 토큰은 초기 손입력 근사값이라 **실제와 다르다**(Figma `#141414` 중성 그레이 vs 코드 `#020618` 남색). 프레임 추출이 필요 |
| **소비처 시각 회귀 없음** | 라이브러리는 어떤 변경이 각 소비처에 중요한지 알 수 없다. 소비 앱 자체 스냅샷이 있어야 "업그레이드하면 우리 화면 뭐가 바뀌나"를 볼 수 있다 |
| **canary 승격 없음** | 이상적으로는 `--tag next` 로 배포 → 소비처 게이트 통과 → `latest` 승격(계약 테스트) |
| **semver 가 시각 변경을 못 담음** | 토큰 색 변경은 API 호환이라 patch 로 나가지만 화면은 크게 바뀐다. 토큰/컴포넌트 분리 배포나 시각 변경=minor 규율이 필요 |
| **복잡 컴포넌트 성숙도** | Calendar·ComboBox 등은 radix/react-aria 가 수년간 다듬은 접근성·엣지 케이스를 따라가지 못한다 |
